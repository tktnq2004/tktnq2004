A hotel booking platform for Vietnam with 360° room tours, map search and booking without an account. Built by a team of two; I wrote most of the Next.js frontend and several backend modules in Spring Boot.

overview

Guests search hotels by province or on a map, walk through rooms in 360° before they book, and pay by card or bank-transfer QR. Hotel owners run their own hotel from a partner portal; platform admins manage everything else.

It is a portfolio project, not a live business: the 400 hotels are seeded test data. The goal was a booking flow that works end to end, correctly and safely, with real payment providers.

what it does

  • Search by province and ward, dates, guests, hotel name, or hotels near you.
  • Map search with MapLibre GL and MapTiler.
  • Hotel and room pages with photos, room types, amenities and policies.
  • Checkout, then card (Stripe) or bank-transfer QR (SePay).
  • Account pages with booking history, and a wishlist.
  • Back offices for admins and hotel partners, including the 360° tour editor.

architecture

The browser never talks to the API directly. Every request goes through route handlers in the Next.js server, which hold the tokens in httpOnly cookies, so page scripts never see them.

One docker compose up starts the web app, the API, MySQL and Redis. The web container sits on a separate network and cannot reach the database.

problems i worked through

Deleting a panorama without breaking the tour

Problem
Hotspots link panoramas together. Deleting one photo could leave other rooms pointing at nothing, and leave orphan files in storage.
What I did
Made hotspots the lowest layer. Deleting a panorama that others link to returns 409 with the list of those hotspots; with cascade=true it removes exactly those. Link rules (a room's panorama may only link to the hotel or the same room) are checked on the server and filtered in the editor. Files on R2 are deleted in one batch, after the database transaction commits.
Result
A tour cannot end up with broken links, and deleting a room or a hotel cleans up its files.

Bookings that only the guest can open

Problem
The first guest flow let anyone view and pay a booking with its sequential id and the guest's email in the URL.
What I did
Designed a new flow: guests confirm their email with a one-time code first and get a guest account with its own tokens. Every booking request checks ownership, and history comes from the token alone.
Status
The frontend is done and the API is written up as a spec. The backend side is still in progress.

One login, two back offices

Problem
Platform admins and hotel owners need very different tools. Two login systems would double the work and the bugs.
What I did
One login route sends each account to /admin or /partner from the hotel it belongs to, and each portal redirects accounts in the wrong place. Menus and buttons follow permissions, so owners and staff need no separate code.
Result
Both portals reuse the same CRUD endpoints, scoped by permission and hotel checks in the service layer.

A payment amount counted twice

Problem
For SePay bank transfers, multi-night stays were multiplied by the number of nights a second time, so the QR code asked for more than the booking cost.
What I did
Traced it to the payment request and the webhook matcher each recomputing the price. Both now read the amount stored on the booking, and the partner dashboard uses the same total.
Result
One source of truth for what a guest owes.

what's next

  • Live payment status while the QR code is on screen.
  • Finish the guest one-time-code flow on the backend.
  • Staff roles per hotel, so owners can manage their own team.
